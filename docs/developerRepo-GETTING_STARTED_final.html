Getting Started — the Framework Repository

Step-by-step setup, from a bare machine to publishing a framework release. This repository (lx-test-kit) holds the reusable REST API testing framework. Consumer projects depend on the published Maven artifact systems.leadex.lxtestkit:framework-bundle and contain only tests, test data and CI configuration.

For the conceptual overview of the architecture, see README.md. This doc is the linear "do these steps in order" path.

0 Prerequisites

The framework resolves all of its own dependencies from Maven Central (the root build declares mavenCentral() only), so building and testing locally needs no GitHub authentication. A PAT is required only when publishing releases (step 13).

1 Clone the repository

git clone https://github.com/ftoropov-leadex/lx-test-kit.git
cd lx-test-kit

A Gradle multi-module project. No additional setup is required before opening it in an IDE.

2 Configure GitHub Packages credentials

Only needed for publishing. Create ~/.gradle/gradle.properties — outside this repository, never committed: 

gpr.user=<github-username>
gpr.token=<PAT-with-write:packages>
chmod 600 ~/.gradle/gradle.properties

The publish config in build.gradle.kts authenticates with the GITHUB_ACTOR / GITHUB_TOKEN environment variables (the CI path). For local publishing, supply the same values — e.g. export them in your shell, or rely on the gpr.user / gpr.token fallback consumed by your environment.

3 Open the project

Open the repository as a Gradle project. Recommended IntelliJ configuration:

SettingValue
Build SystemGradle
Gradle JVMJava 21
Run tests usingGradle

Run tests using Gradle is mandatory, not cosmetic. The test task's doFirst injects the aspectjweaver as a JVM -javaagent — the AspectJ Load-Time Weaving the reporting module relies on. The IDE's native TestNG runner bypasses it.

Each published module focuses on a well-defined set of concerns:

ModuleResponsibility
framework-coreHTTP client abstraction, configuration, URL resolution, runtime model classes
framework-test-supportBase test classes, fluent request builder, assertion DSL, retry mechanism, schema & snapshot validation
framework-reportingAllure integration, automatic HTTP attachments, AspectJ instrumentation, logging integration
framework-splunkSplunk client, polling utilities and assertion DSL
framework-bundleUmbrella artifact re-exporting all public framework modules

Consumer repositories depend only on framework-bundle. The remaining modules are implementation details.

Note: only the five modules above are wired in settings.gradle.kts and therefore built/published. Other module directories you may see on disk (e.g. framework-db-oracle, framework-messaging-rabbitmq) are not included in the build and are not published — treat them as inactive until added to settings.gradle.kts.

6 Verify the project builds

./gradlew help

Evaluates the Gradle configuration of every module (the configuration phase) without compiling or running tests — a fast sanity check that the build scripts are well-formed and the Java 21 toolchain is resolvable. If this fails:

  • verify Java 21 is being used;
  • refresh Gradle dependencies (./gradlew --refresh-dependencies).

7 Build the framework

./gradlew clean build

This runs the complete verification pipeline:

  • compiles every module;
  • compiles and verifies all modules (no module-level tests are present yet — the test task is a no-op);
  • packages every artifact (including the javadoc and sources jars — the build applies withJavadocJar() / withSourcesJar());
  • prepares publishable Maven packages.

A successful clean build confirms the framework is in a releasable state.

9 Generate Javadoc

There is no aggregate-javadoc task. Each module produces its own Javadoc. To generate it for a module: 

./gradlew :framework-core:javadoc

Output is written per module:

framework-core/build/docs/javadoc/

A clean build (step 7) also packages a javadoc jar for every module via withJavadocJar(). Review newly introduced public APIs before a major release.

10 Publish the framework locally

When iterating on a change before cutting an official release, publish to your local Maven repository. The command is the same on all platforms: 

./gradlew publishToMavenLocal

macOS / Linux

Artifacts land under:

~/.m2/repository/

Windows

Artifacts land under:

%USERPROFILE%\.m2\repository\

A consumer project can then temporarily resolve the framework from there by adding mavenLocal() to its repositories — useful when co-developing a framework change against a real consumer before publishing. 

repositories {
    mavenLocal()
    mavenCentral()
}

Typical development loop

edit module  →  :module:build  →  ./gradlew build
      →  publishToMavenLocal  →  validate from consumer repo

11 Verify a local publication

Confirm the artifacts installed under the framework's group coordinates:

macOS / Linux:

~/.m2/repository/systems/leadex/lxtestkit/framework-bundle/

Windows:

%USERPROFILE%\.m2\repository\systems\leadex\lxtestkit\framework-bundle\

A complete local publication includes all five published modules:

  • framework-core
  • framework-test-support
  • framework-reporting
  • framework-splunk
  • framework-bundle

If any module is missing, verify it is listed in settings.gradle.kts and that the maven-publish plugin applies to it.

12 Bump the framework version

The version is a single source of truth: the version assignment in the subprojects { … } block of build.gradle.kts — it applies to every module at once. 

subprojects {
    group   = "systems.leadex.lxtestkit"
    version = "1.0.5"   // ← bump this
}

GitHub Packages does not allow overwriting an existing version. Publishing the same version twice fails. Increment the version immediately before publishing, after all development and verification is done.

Bump the version number in build.gradle.kts and in any version strings in README.md. Commit the change before publishing.

The version shown in this guide (1.0.5) is for illustration only. The actual framework version will differ. Always check the current version in build.gradle.kts subprojects block — it is the single source of truth for the framework version; README.md only mirrors it in consumer dependency examples.

13 Publish to GitHub Packages

After bumping the version (step 12), publish with: 

./gradlew clean build publish

This builds every module, runs the verification pipeline, generates Maven metadata, and uploads each published module to https://maven.pkg.github.com/ftoropov-leadex/lx-test-kit. Requires GITHUB_ACTOR + GITHUB_TOKEN (or the gpr.user / gpr.token fallback from step 2).

★ Full release workflow (end-to-end)

This is the canonical release path. Follow these steps in order every time you ship a new framework version.

feature branch  →  implement  →  ./gradlew build  →  publishToMavenLocal (optional)
      →  validate with consumer repo  →  merge to main
      →  bump version  →  ./gradlew clean build publish  →  tag & push  →  update consumer

14 Verify the published release

After publishing:

  • the package appears on the repository's GitHub Packages page;
  • the expected version is visible;
  • every published module was uploaded;
  • consumers can resolve the new version.

Quick validation — bump the framework version in a consumer repo and run:

./gradlew help

If dependency resolution succeeds there, the publication is good.

15 Validate the framework in a consumer project

Before announcing a release, validate it against a real consumer repository:

  • update the framework dependency & reload Gradle;
  • execute a representative test suite;
  • verify generated Allure reports, retry behaviour, logging and HTTP communication.

Testing against a real consumer is the most reliable way to catch integration regressions before the release reaches other teams.

16 Troubleshooting

Build fails

Verify Java 21 is selected, the Gradle wrapper is used, and dependencies resolve. Refresh if needed:

./gradlew --refresh-dependencies

Publishing fails

Common causes:

  • attempting to publish an already-existing version (no-overwrite rule — bump first);
  • token missing write:packages, or GITHUB_ACTOR / GITHUB_TOKEN not set;
  • network interruption during upload.

Tests behave differently in the IDE

Set Run tests using: Gradle and Gradle JVM: Java 21. The native IDE runner bypasses the AspectJ weaver injected by the Gradle test task, so reporting/ instrumentation will differ.

Generated reports are missing information

Verify tests ran through Gradle, Allure result directories were produced, and stale report output was cleared before regenerating.
