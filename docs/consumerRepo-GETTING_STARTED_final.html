Getting Started — A consumer repository

Step-by-step setup, from a bare machine to a green test run. This repo holds tests; the framework (HTTP client, assertion DSL, Allure reporting, retry, TestNG listeners) ships as the published Maven artifact lx-test-kit (systems.leadex.lxtestkit:framework-bundle).

ToolRequirementCheck

1 Get the repo

Option A clone an existing repo:

macOS / Linux:

git clone https://github.com/ftoropov-leadex/test-storage-bae.git
cd test-storage-bae

Windows (PowerShell / cmd):

git clone https://github.com/ftoropov-leadex/test-storage-bae.git
cd test-storage-bae

Option B set up from scratch (no existing repo):

  1. Create a new repository on GitHub.
  2. Initialize it locally:

    macOS / Linux:

    mkdir my-test-repo && cd my-test-repo
git init

    Windows (PowerShell / cmd):

    mkdir my-test-repo
cd my-test-repo
git init
  3. Copy the Gradle build files (build.gradle.kts, settings.gradle.kts, gradle.properties), the test-suites/ structure, and .github/workflows/ from this guide's reference layout.
  4. Commit and push.

2 One-time credentials setup (for local runs)

Create gradle.properties — outside this repo, never committed:

gpr.user=<github-username>
gpr.token=<PAT-with-read:packages>

macOS / Linux:

chmod 600 ~/.gradle/gradle.properties

Windows (PowerShell):

# Restrict access to the current user only
icacls "$env:USERPROFILE\.gradle\gradle.properties" /inheritance:r /grant:r "$env:USERNAME:(R)"

The credentials block in build.gradle.kts reads GITHUB_ACTOR / GITHUB_TOKEN env vars first (CI path), then falls back to these gpr.user / gpr.token properties (local path).

3 Pin the framework version

gradle.properties:

lxtestkit.version=1.0.5

Every suite pulls framework-bundle:${lxtestkit.version} via test-suites/build.gradle.kts. Bump this one line when a new framework version publishes, then Gradle-reload.

Set the actual framework version at gradle.properties.

No manual classpath tweaks, no local framework sources — the Gradle dependency declaration is the single source of truth for which framework version your tests run against.

4 Verify the toolchain resolves

./gradlew help

Resolves dependencies and proves the PAT + Java 21 toolchain work, without running tests yet. If this fails on framework-bundle resolution → re-check step 2 (PAT scope / ~/.gradle/gradle.properties).

5 Understand what one suite needs

A suite (test-suites/<suite-name-example>/) is wired from four pieces:

  1. Endpoint registry — test-suites/resources/domains.properties:

    api.endpoints.get-exampleByDate.method=GET
api.endpoints.get-exampleByDate.reUrl=/api/customer/search

  2. TestNG suite XML — src/test/resources/testng-<suite-name>.xml. Listeners are declared on the framework side; the suite XML only needs the test class list.

  3. Test class — extends BaseApiTest, declares domain(), calls call("<endpoint-id>", …) and asserts with the lambda-scoped DSL.

  4. Schema + snapshot — src/test/resources/schemas/*.schema.json and snapshots/*.json, used by matchesSchema(...) / matchesSnapshot(...).

Suite registration: settings.gradle.kts auto-registers every suite dir that has its own build.gradle.kts. Mirrors CI find test-suites -name build.gradle.kts discovery — filesystem presence is the single source of truth. Drop a suite in, no settings edit needed.

A per-suite build.gradle.kts only needs plugins { id("java") } — the framework dependency and the TestNG suite XML path (testng-<suite-name>.xml) are applied from the parent test-suites/build.gradle.kts via convention. See the reference layout for the exact one-liner.

Import the framework in test classes

When you write a new test class, import the framework library from the published Maven artifact, not from a local JAR or source copy.

Why the published artifact?

  • The framework ships as a versioned Maven artifact (systems.leadex.lxtestkit:framework-bundle). Your test classes compile against the exact version declared in gradle.properties, ensuring reproducibility across machines and CI.
  • Local JARs or classpath hacks bypass dependency management — they can silently drift from the version the rest of the team uses, causing hard-to-diagnose runtime errors.
  • Gradle resolves the artifact from GitHub Packages (authenticated via the PAT from step 2), so every developer and every CI run gets the same bytecode.

How to import

  1. The framework dependency is declared in the parent test-suites/build.gradle.kts and applied to all suite subprojects: 
    // test-suites/build.gradle.kts
subprojects {
    plugins.withId("java") {
        dependencies {
            "testImplementation"("systems.leadex.lxtestkit:framework-bundle:${property("lxtestkit.version")}")
        }
    }
}

    The same parent also derives the TestNG suite XML path by convention (testng-${project.name}.xml). A per-suite build.gradle.kts only needs the java plugin marker; everything else is inherited.

  2. In your test class, import from the framework packages: 
    import io.leadex.aqa.testsupport.base.BaseApiTest;
import io.leadex.aqa.testsupport.assertions.ApiResponseAssert;

public class MySuiteTest extends BaseApiTest {
    @Override
    protected String domain() { return "my-suite"; }
    // ...
}

6 Set the runtime env vars

The framework reads these at startup via ConfigResolver. For the full variable table, see README.md.

For local runs

macOS / Linux (zsh/bash):

export FRAMEWORK_ENV=uat
export FRAMEWORK_BASE_URL=https://<sandbox-host>
export FRAMEWORK_DOMAINS_PATH="$PWD/test-suites/resources/domains.properties"
export FRAMEWORK_CLIENT_NAME=<client>
export FRAMEWORK_CLIENT_SECRET=<secret>

Windows (cmd):

set FRAMEWORK_ENV=uat
set FRAMEWORK_BASE_URL=https://<sandbox-host>
set FRAMEWORK_DOMAINS_PATH=%CD%\test-suites\resources\domains.properties
set FRAMEWORK_CLIENT_NAME=<client>
set FRAMEWORK_CLIENT_SECRET=<secret>

For CI (GitHub Actions)

Variables and secrets are configured in the GitHub repository — no local export needed. See README.md for the full list and where each lives (per-environment variables, per-environment secrets, repository-level variables/secrets).

7 Run tests

Option 1 local (macOS / Linux)

Whole suite:

./gradlew :test-suites:<suite-name>:test

Single test:

./gradlew :test-suites:<suite-name>:test --tests "<fully.qualified.TestClass.testMethod>"

Option 2 local (Windows)

Same Gradle commands work in PowerShell / cmd — use gradlew.bat instead of ./gradlew:

gradlew.bat :test-suites:<suite-name>:test

Important: Always run tests through Gradle (./gradlew test or gradlew.bat test). The test task injects the aspectjweaver as a JVM -javaagent in its doFirst, which enables AspectJ load-time weaving. Running through IntelliJ's native TestNG runner bypasses this.

Option 3 CI (GitHub Actions)

Trigger a workflow dispatch run — see section 9 below and README.md.

8 Generate the Allure report

./gradlew allureReportWithTests
./gradlew allureServe

allureReportWithTests runs every suite (runSuitesForAllure), aggregates each suite's allure-results into a single report, and carries trend history/ forward. The allureReport task auto-clears the stale report dir on re-run (its doFirst), so repeated local runs don't hit Allure's "target directory already in use" error.

You cannot open Allure's index.html directly — it requires a local HTTP server. ./gradlew allureServe starts one and opens the report in your browser automatically.

9 (CI) Run it on demand

CI is workflow_dispatch only — .github/workflows/runTests.yml. Trigger a run, pick environment and suites; the report job aggregates all suites into one Allure report and (when publish_report) deploys to cloud web-hosting.

Setting up the CI workflow

  1. Create GitHub Environments (Settings → Environments) for each target env (e.g. uat, preprod).
  2. Populate per-environment secrets (FRAMEWORK_CLIENT_NAME, FRAMEWORK_CLIENT_SECRET).
  3. Populate per-environment variables (timeouts, retry config).
  4. Add repository-level secrets (PACKAGES_READ_TOKEN for framework resolution, cloud hosting API token).
  5. Add repository-level variables (base URLs per env, timeouts, etc.).
  6. Edit runTests.yml to add new environments to the environment input's options list and extend the base-URL selection expression, or modify it to suit the needs of the project.

Full input/job/variable reference: README.md.
